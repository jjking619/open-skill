# Code Authoring

## Use When

- 写新功能。
- 修改非本次会话新建的既有代码。
- 需要控制 diff，避免顺手改动淹没真实变更。

不要用于纯 review、TDD 流程本身、一次性 spike 或提交后的批量清理。

## Priority

- 项目既有风格 > 本技能默认值。
- 正确性与安全性 > 最小 diff。
- 根因修复 > 为了过测试做表面补丁。

## Agent Loop

1. 先读局部上下文：命名、注释语言、错误处理、测试位置、调用点。
2. 先找最近验证：目标测试、最小复现命令、窄范围 lint/typecheck、局部构建。
3. 说清任务：一句话写明缺陷/需求和验收标准。
4. 缩小范围：只改目标代码、直接调用点、必要测试和被直接影响的派生产物。
5. 直接落地：沿用既有风格，不顺手重构，不扩接口，不引入无关依赖。
6. 立刻验证：先跑最相关的检查；跑不了就记录原因并给替代证据。
7. 再交付：说明改了什么、为什么必需、怎么验证的。

## Guardrails

- 禁止为了让测试变绿而加特判、hardcode、绕过校验、注释断言。
- 禁止无关格式化、重命名、import 排序调整、跨文件大搬家。
- 允许必要的输入校验、异常处理、资源释放、调用点同步更新、快照/生成物更新。
- 发现无关问题只记录，不顺手修，除非用户明确同意。

## Comments

- 语言跟随文件既有风格；新文件默认英文。
- 注释优先写 why、边界条件、单位、副作用、来源依据。
- 参数/返回/异常这类 what，仅在既有规范要求的 API 文档、公共接口文档或稳定契约里写。
- 不写提示词、需求原文、对话内容、AI 署名、日期式变更日志、死代码注释、空泛 TODO/FIXME。

```bash
# Comment candidates: review manually after search
grep -RInE "由 ?AI|AI[- ]?generated|as requested|按用户要求|[0-9]{4}-[0-9]{2}-[0-9]{2}|TODO|FIXME" .
```

## Done Check

- [ ] 改动前有最近验证记录，或有无法实跑的原因与替代证据。
- [ ] diff 只覆盖必须改的代码、调用点、测试和直接受影响的生成物。
- [ ] 注释语言和仓库风格一致，且没有禁止项。
- [ ] 每处改动都能用一句话说明必要性。
- [ ] 已完成行为级验证；若没有，已明确说明原因。
