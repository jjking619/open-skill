# md → 飞书文档直写的坑与自检（含对 `sync-md-to-existing-doc.md` 第 5 步的口径修正）

配套 `sync-md-to-existing-doc.md`（把任意 md 原地写进用户指定云文档）使用。
2026-10-02 实测新增，**优先看本文件的核对口径**。

## 1. 绝不在 md 里嵌套代码围栏 ← 最贵的坑

发布脚本的 `parse_md` 判定围栏是朴素匹配：**行首 ``` 起 → 下一个行首 ``` 止**。
若一个 ```markdown 块**内部**再出现 ```，外层块会**提前闭合**，其后内容全部退化成普通段落，
整段以纯文本写进文档（表格也变成 `|` 文本行）。

**触发场景**：文档里要展示「可直接复制的 md 示例」——例如附录给三份可复制使用的 SKILL.md。
这些示例天然含代码块，最容易踩。

**对策**：内层不要用围栏。
- 目录树 / 清单 / 产物结构 → 写成普通行或表格；
- 代码 → 用「文件名 + 说明」表述，或只在正文给片段。

## 2. 推云前先本地跑 `parse_md` 自检（比写完再回读便宜得多）

```python
# 用发布脚本的 parse_md 做本地自检 → 得到期望块数
blocks = g["parse_md"](open(MD, encoding="utf-8").read())
# ① 块型分布（H1/H2/H3 数、代码块数、引用数、分隔线数）
# ② 找「文本块(block_type==2)内容里含 ```」的异常块 —— 数量 > 0 就是围栏破损，别推
```

两个副产品，直接用于写后核对：
- 期望**顶层块总数** = `len(blocks)`；
- 期望**表格数** = `len([b for b in blocks if "__table__" in b])`。

中英两稿都跑一遍还能一键验证结构一致（两侧 H1/H2/H3、代码块、表格、总块数全部相等）——
这比"看起来一样"可靠，也是交付时可以说出口的客观证据。

## 3. 核对口径修正：表格数别用 raw `grep`

`sync-md-to-existing-doc.md` 第 5 步原写「表格块数必须等于 md 里 `|---|---|` 分隔行数」。
**该口径在文档含代码块示例时会虚高**（实测：真实 5 个表，raw grep 数到 15，因为定义示例里
也含分隔行）。正确口径二选一，并两者比对：

- `parse_md` 数出的 `__table__` 数；
- 云端回读 `block_type == 31` 的块数。

其余核对项不变：顶层块末块不应停在表格上；顶层块数 = 解析块总数。

## 4. 其他要点

- **`--doc <obj_token>` 是幂等的**：稿子改了就直接重发（先清空全部子块再重写，**URL 不变**），
  不必换链接、不必新建文档。节点标题不受影响，md 的 H1 只成为文档内第一个标题块。
- **权限探活**：先 `GET /wiki/v2/spaces/get_node?token=<wiki_token>` 取 `data.node.obj_token`，
  返回 `code=0` 才动手；`131006` = 应用不是该节点协作者 → 请用户把应用加成**可编辑**，
  授权后重试一次即通过（不必换链接或新建文档）。
- **不要把非报告类稿子写进台账类表格**（明细表只用于留痕）。
- **中等篇幅稿前台跑得动**：165 顶层块 + 5 表格几十秒完成，`timeout=600` 的前台调用足够；
  真正需要 `background=true` 的是「一次调用连跑多篇」的场景。
- 回读时**必须翻页**（按 `has_more` 循环），别把单页 500 当成总数。
