# 报告 md → 飞书知识库的渲染约定

报告 md 既要在本地编辑器里好看，又要在飞书知识库里渲染成原生块。
发布脚本只认下面这些语法，其余一律退化成普通段落（表格会变成一堆 `|` 文本，很难看）。

## 语法支持矩阵（实测）

| md 写法 | 飞书块 | 备注 |
|---------|--------|------|
| `#` `##` `###` `####` | 标题 1–4 | 只解析到 4 级 |
| `> 文本` | 引用块 | 每行一个块，适合放扫描日期/范围/依据 |
| `- [ ]` / `- [x]` | 待办（复选框） | 修复清单、修复步骤首选，可勾选 |
| `- ` / `* ` | 无序列表 | |
| `1. ` / `1) ` | 有序列表 | |
| `---` | 分隔线 | |
| ```` ```lang ```` | 代码块（多行） | lang 见下表；多行内容用单个 text_run 传 `\n`，实测正常 |
| `\| a \| b \|` + `\|---\|---\|` | 原生表格 | **单表上限 9 行（含表头）**，超出自动拆表并重复表头 |
| `**粗体**` | 加粗 | 行内样式 |
| `` `行内代码` `` | 行内代码 | |
| `[文字](URL)` | 超链接 | URL 会自动 percent-encode |

### 代码块 language 枚举（常用）

`text`=1 · `bash`=7 · `c`=10 · `cpp`=9 · `css`=12 · `dockerfile`=18 · `go`=22 · `html`=24 · `java`=29 · `javascript`=30 · `json`=28 · `makefile`=38 · `markdown`=39 · `php`=43 · `powershell`=46 · `python`=49 · `ruby`=52 · `rust`=53 · `sql`=56 · `shell`=60 · `typescript`=63 · `xml`=66 · `yaml`=67 · `cmake`=68 · `diff`=69 · `toml`=75

未收录的语言回落到 `text`（纯文本），不影响内容。

## 两个执行模式

- 首次发布：`<发布脚本> <报告.md> --date YYYY-MM-DD` → 在知识库**按日期归档的目录 `YYYY-MMDD`**（如 `2026-0905`，与同批检查报告同层）下建节点，打印 wiki URL。
  归档目录由 `--date` 推导（`2026-09-05` → `2026-0905`），不传则用当天；目录不存在会自动建
- **原地改版**：`<发布脚本> <报告.md> --doc <DOC_ID>` → 先清空该文档全部子块再重写，**wiki URL 不变**（已发出的报告链接不会失效）
- 试渲染：`--no-wiki` 只建普通 docx（如 `https://<tenant>.feishu.cn/docx/<id>`），验证完删掉即可

## 实测坑（都已在脚本里规避）

- 单表 `row_size` 上限 9（含表头行）；10 行直接报 `1770001 invalid param`。脚本按「表头 + 8 行数据」分段并重复表头。
- 表格块 `property` 里给 `header_row: true` 合法；空 `table: {}` 报 `99992402`。
- **列宽必须自己算**：不传 `column_width` 时飞书默认每列 100px（总宽 500），短文本也会被挤成多行。
  脚本按内容算列宽（CJK 记 2 单位、西文 1 单位，7px/单位 + 16px 内边距），短列给足最小宽度、
  宽列分掉剩余空间，总和固定在 830px（docx 正文宽度）。内容确实超宽时才会换行。
  写 md 时把表头/单元格文字写紧凑（如「目录」只写一侧路径）能把宽列让出来，避免换行。
- 单元格内容：表格创建后飞书会自动为每个单元格建一个空文本块。**改这个空块要用 PATCH `/blocks/{cell_inner_block_id}` + `update_text_elements`**（粗体/行内代码/链接样式都实测可用）；往单元格里 POST 新块会多出一个空段落。
- 删块：`DELETE /docx/v1/documents/{doc}/blocks/{parent}/children/batch_delete`，**区间必须放在 JSON body**（`{"start_index":0,"end_index":n}`）——放 query 里报 `99992402`。
- **写用户指定的既有文档前先探活权限**：`GET /wiki/v2/spaces/get_node?token=<wiki_token>` 取 `obj_token` 作为 `--doc` 的目标；
  若返回 `131006 node permission denied, tenant needs read permission`，说明该文档还没把应用加为协作者（`/wiki/v2/spaces` 列表为空也是同一原因），
  需请人在前端「分享 → 添加协作者」里搜索应用（机器人）名并给「可编辑」（或把应用加入该知识库空间成员），不能靠换端点绕过。
- 知识库节点删除：应用无 `wiki:node` 删除权限（`99991672 Access denied`）。所以要改报告一律用 `--doc` 原地更新，别发新节点；确需删除旧节点由人在前端操作。
- 代码块多行内容写进单个 `text_run.content`（含 `\n`）实测正常，不需要拆成多个 element。

## 写报告的建议

- 顶部用 3–5 行 `>` 引用交代：生成日期（**带时分**）、范围、现象、依据。
- 结论用一行 `**合计……**`，再进表格；表格超过 9 行不必手动拆，脚本会拆。
- 中英镜像的清单建议**合并成一张表两列**（中文文档 / 英文文档），比中英各一张表省一半篇幅，也便于成对修复。
- ⚠️ **问题清单不要贴代码块原文**（实测踩坑：把每个问题块的 preview 贴进列表，
  ① 同文档多个块内容相同 → 重复展示；② preview 里的 `\n` 转义在飞书渲染成真实换行，把列表撑乱）。
  正确写法：列表格 `文档 | 位置 | 粘连处数 | 粘连类型 | 链接`，需要原文就让读者点链接。
  粘连类型用短语概括（如「#include 头文件链粘连」「注释与命令粘连」）。
- 修复动作、留痕登记用 `- [ ]` 待办块，飞书里可直接勾选，兼作派单队列。
- 报告 md 的 H1 会成为知识库节点名，建议统一成 `[文档名] 报告类型`（如 `[某文档] 检查报告`），
  专项清单写成 `[全库] 专项名`；归档目录按天 `YYYY-MMDD`，同一批报告同层。
