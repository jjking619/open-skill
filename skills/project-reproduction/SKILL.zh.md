# 复现项目 Skill（按原文复现 → 最优排障 → 报告产出）

## 适用场景（When to Use）

- 按 README / 教程 / install.sh 复现、部署、跑通某个项目、demo、开源代码
- 需要逐步执行 README / 教程 / install.sh，并记录每步结果与偏差
- 复现过程报错，需要系统化排障、留痕，并交付「报告 + 修改后文件」

> **不要用于**：纯代码审查或改需求；已有明确单点 bug 的直接修复；一次性实验验证思路。

## 技能承诺（先读这段）

把一份项目（源码 + README/教程/install.sh）按“原文”一步步复现跑通：过程全程留痕，报错走最优路径解决并把修复固化到文件里，最后生成复现报告和修改后文件，输出到与用户约定的输出目录（不要写桌面）。

本技能保证的是 **“过程可预测、结果可复用”**：任何一次复现的产出，都应让“下一次按报告 + 修改后文件”能一次通过。

## 前置条件（Prerequisites）

- 输出根目录：与用户约定的 `<输出目录>`（复现产物统一落此；不要写桌面）
- 目标环境为嵌入式板卡（adb）时，配合本仓库的 `adb-device-toolkit` 技能一起用

## 产出目录结构（开始前先建好）

```text
<输出目录>\复现结果_<项目名>_<YYYYMMDD_HHMM>\
├─ 先读我_通俗总结.md    # 面向人的总览（必出）：一句话结论 / 怎么用 / 文件地图，用户先看这个
├─ 00_复现报告.md        # 主报告（结构见附录）
├─ 01_执行日志.md        # 逐步留痕，边做边 append，禁止最后补写
├─ 02_问题与修复记录.md  # 每个报错一条完整记录
├─ 03_修改后文件\        # 最终可用文件，保留原相对路径
└─ 04_原始快照\          # 原文副本 + 修改前的原始文件 / git commit，供 diff
```

## 执行流程（Procedure）

### P0 准备

1. **收集并通读原文**：README/教程/install.sh 全文、源码位置、目标环境类型（本机 / adb 板子）。
2. **确认验收标准**：与用户确认“复现成功”的定义——哪个命令、哪种现象算通过（如 `python3 main.py` 正常退出、页面可访问、日志出现某关键词）。没有验收标准就无法判断“最优”。
3. **建工作区目录**；原文与关键原始文件复制进 `04_原始快照`（有 git 则记录 commit hash）。
4. **环境快照写入 `01_执行日志`**：
   - 本机：OS、解释器版本（注意 `python3` 与 `python` 可能是不同解释器）、依赖清单、网络/代理、当前目录
   - 板子额外记录：adb 连接状态、当前 shell 身份（`adb shell whoami`，通常是 root）、板上实际使用的普通用户名（`adb shell "ls /home"`，常见 pi）

### P1 按原文逐步执行（忠实原文）

先判定“原文的执行身份”：文档里的命令是以哪个用户视角写的？（`~` 指向 `/home/<user>` 还是 `/root`？`python3` / `pip` 是谁的环境？）

板子 adb 默认以 root 执行，但项目文档通常按 pi 等普通用户视角编写——root 下“跑通”不等于目标用户下能跑。执行身份与原文视角不一致时，先按目标用户身份等价执行（root 跑但强制 `HOME=/home/<user>` 并事后 `chown` 回属主，或切到目标用户再跑）。实际用户名记自 P0.4 的 `ls /home`，不要写死 pi。

5. **拆解步骤**：把原文拆成步骤序列。每步记录：原文原句 → 执行命令（按原文字面执行，不预改）→ 实际输出 / exit code / 耗时 → 判定通过或偏差。
6. **忠实原文**：遇到原文与现状不符（路径不存在、命令本身就报错）：先按原文字面执行一次并记为“文档偏差”，不要提前替作者修正。
7. **边做边记**：每步完成立即 append 到 `01_执行日志.md`（防中断丢失）。条目格式示例：

   ```text
   ### 步骤3 安装依赖（原文：pip install -r requirements.txt）
   - 原文：...
   - 命令 / 退出码：... / 0
   - 结果：通过 | 失败 | 偏差（说明）
   ```

8. **通过标准**：实际结果与原文描述一致，且满足 P0 的验收标准。

### P2 报错 → 最优路径（核心）

9. **捕获完整证据**：原始报错全文 + 堆栈 + exit code + 相关日志文件路径。禁止只记一行摘要或“翻译后”的报错。
10. **归因顺序**（按成本从低到高，一次只试一个分支）：
    - **a. 环境差异**（最常见）：依赖/解释器/OS 版本不符、缺包、网络代理、权限 → 先做“文档声明版本 vs 实际版本”比对表
    - **b. 配置问题**：config.yaml / 路径 / URL / 端口 / 密钥
    - **c. 代码与文档不符** → 最小补丁
    - **d. 平台特有坑**：查本技能 Pitfalls；Windows 落盘问题看 `windows-file-tooling`；板子问题查目标板卡对应的运维技能
11. **止损原则**：同一分支重试 ≤2 次仍无进展必须换分支或暂停上报；禁止对同一错误无限重试。
12. **最小修改 + 可固化**：一次只改一处；优先把修复写进项目文件本身（install.sh / config / 源码 / 文档勘误），禁止只用一次性手工命令绕过——修复必须固化，让“将来别人按原文装”不再踩同一坑。涉及中英文成对文档时两版同步修正。
13. **改完即验即记**：每处修改后立即重跑失败步骤及依赖它的后续步骤验证；随即写入 `02_问题与修复记录.md`。条目格式示例：

    ```text
    ### Q1 pip install 报 No matching distribution
    - 报错原文：...
    - 归因：环境差异(a)：文档要求 Python3.11，实际 python3 为 3.8.5
    - 修复（固化位置）：install.sh 第 X 行增加用 pyenv/uv 装 3.11 的步骤
    - 验证：重跑步骤3通过，后续步骤 4-6 未受影响
    ```

### P3 收尾与产出

14. **全量重跑**：重跑关键链路（或至少重跑受影响完整链路），确认终态与验收标准一致。
15. **生成修改清单与 diff**：优先 `git diff`；无 git 时用 `03_修改后文件` vs `04_原始快照` 逐文件对比。
16. **生成报告**：
    - `00_复现报告.md`（结构见附录）：项目信息 / 复现环境 / 验收标准 / 步骤结果表 / 问题与修复表 / 修改文件清单 / 结论 / 再次复现指引
    - `先读我_通俗总结.md`（面向用户的 1-2 屏总览，大白话无行话，**每次必出**——用户文件一多就找不到重点），内容含：
      ① 一句话结论
      ② 做了什么
      ③ 你现在怎么用 / 怎么验证（可直接照做的命令）
      ④ 遇到的问题一句话解释
      ⑤ 文件地图：明确标出「重要（看这个就行）」vs「修改成果」vs「过程记录（一般不用翻）」
      ⑥ 遗留事项
17. **归档最终文件**：把最终可用文件复制进 `03_修改后文件\`（保留相对路径）。报告中显著标注：若不使用修改后文件，哪些步骤按原文必然失败。
18. **汇报**：只给输出目录绝对路径 + 结论摘要（按原文通过 / 修复后通过 / 未复现及原因）+ 遗留风险，不要把整份报告贴进对话。

## 常见坑（Pitfalls）

- **adb 与外设互斥**：adb 连着时 USB-host 外设（摄像头等）枚举不到属互斥特性，不是故障；验收建议以「出厂默认终端直接 `python3 main.py` 能跑通」为准（不依赖绝对路径解释器、不改默认 shell）。
- **执行身份**：adb 默认身份是 root，但项目通常按普通用户（pi 等）视角编写：root 的 `~` / `python3` / `pip` 与普通用户是完全两套环境（root 默认 `HOME=/root`，pip 装的包 pi 看不到）。执行、装依赖、验收都要带上目标用户身份；root 跑通必须再以目标用户身份复验才算通过。
- **长任务**：长安装/构建用 `background=true` + `notify_on_complete`，不要前台盲等；服务器类进程起来后做 health check 再继续。
- **别相信脚本的"成功"自述**：把子进程输出重定向到不存在的目录（如 `> logs/x.log` 而 `logs/` 不存在）会让子进程**根本不启动**，但脚本仍打印 "Programs started / All done" —— 看脚本自述会误判通过。判定前必须验证副作用：产物文件、进程是否存活（CPU 时间是否增长）、日志是否真的写入。某 demo 的 build.sh 就是这个坑（`mkdir -p logs` 被注释掉了）。
- **执行身份 ≠ 环境身份**：以非交互 shell（`su -c`、`bash -lc`、ssh 单命令）跑项目脚本时，目标用户 `~/.bashrc` 里的 PATH 往往不生效（Debian 的 .bashrc 对非交互 shell 直接 early-return），于是 `python3` 落到系统版 → 报缺依赖（如 `No module named evdev`）被误判成项目问题。要复现"用户在终端里跑"的效果，必须显式 `export PATH="$HOME/.pyenv/shims:$HOME/.pyenv/bin:$PATH"` 之类的 PATH。
- **adb 传二进制一律用 `adb push`**：`adb shell "cat > file"` 走的是 pty，二进制会被回显/污染（实测把 19MB tar.xz 传成垃圾）；传完用 md5sum 双边核对。文本小文件可用 base64 管道。
- **远端长任务与 reboot**：用 `setsid … > log 2>&1 < /dev/null &` 脱离 adb 会话再轮询日志；`(sleep 2; reboot) &` 这类后台子进程会随会话退出被回收而**静默不生效**，重启用 `systemctl --no-block reboot`。
- **MSYS 路径**：git-bash 里原生 Windows 工具不收 MSYS 路径：给 git/python 等传 `C:/xxx` 或 `/d/xxx` 风格路径；`cd` 是 bash 内建不受此限。
- **报错留原文**：报错优先保留原文文本，不要边看边翻译摘要，防止丢信息。
- **磁盘满**：目标设备根分区小且出厂即满（如 8G），装依赖报磁盘满时先 `df` 检查，别误判为缺包。

## 完成度自检（Verification）

- [ ] `01_执行日志` 逐步覆盖原文全部步骤（含原文引用与实际结果），非事后补写
- [ ] `02_问题与修复记录` 覆盖每个报错，且修复已固化进文件（不是一次性命令）
- [ ] `03_修改后文件` 存在，与报告修改清单一一对应
- [ ] `先读我_通俗总结.md` 已生成：含一句话结论 + 文件地图（面向人、大白话，非流水账）
- [ ] `00_复现报告` 结论明确（按原文通过 / 修复后通过 / 未复现+原因）；按“报告 + 03_修改后文件”能再次复现成功
- [ ] 验收在“目标用户身份”下完成（板子：pi 等普通用户身份复验通过，而非仅 adb root 跑通）
- [ ] 输出目录已建在约定路径下，并把绝对路径告知用户

## 附录：复现报告结构（`00_复现报告.md`）

```
1 基本信息      复现日期 / 原文来源（README·教程·install.sh 的路径或 URL）/ 源码位置与版本 / 目标环境类型
2 复现环境      OS 与版本 / 解释器版本（python3 与 python 分别列）/ 依赖清单 / 网络与权限 / 设备额外项（型号、连接状态、固件、根分区剩余）
3 验收标准      与用户确认的「跑通」定义：哪条命令、哪种现象、哪个输出算通过
4 执行步骤与结果 表格：# | 原文步骤（原句） | 执行命令 | 结果（通过/失败/偏差） | 备注（耗时、观察）
5 问题与修复记录 表格：# | 报错原文节选 | 根因（归因分支 a/b/c/d） | 修复内容与固化位置 | 验证方式与结果
6 修改文件清单   表格：相对路径 | 改动摘要 | 类型（修复/勘误/新增） | 是否必须使用（不用则哪一步必然失败）
7 结论          完全按原文通过 / 修复后通过（共 N 处，见第 6 节）/ 未复现（卡在哪一步、原因、建议）
8 再次复现指引   ① 用 03_fixed-files 覆盖对应位置 ② 按 01_执行日志 中标「通过」的步骤顺序执行 ③ 预期结果（与第 3 节一致）
```

写报告的两条纪律：**结论先行**（一句话结论放最前）；**报错留原文**（不要边看边翻译摘要，防丢信息）。
